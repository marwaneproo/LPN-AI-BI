⚠️ Three framing corrections up front

Verified against the actual codebase — a new joiner needs the real map, not the aspirational one:

“.NET 9 components”

services-dotnet/gateway and services-dotnet/reporting are empty placeholders (only .gitkeep files); poc-dotnet-archive/ is just a README. There is no running .NET service today. The live backend is Java (Spring Boot) + Python (FastAPI).

“824 tables”

That is the upstream Compiere ERP catalog. What this system actually models is far smaller: ~38 documented entities (docs/schema_metadata.csv), ~18–25 core business tables, plus a purpose-built star-schema warehouse.

“5 years of historical data”

The forecasting data spans ~24–25 months (≈ 2024-06 → 2026-06) — two seasonal cycles. Prophet requires ≥12 complete months, which is exactly what makes company-level forecasting viable.

The 1-Minute Pitch

Why this exists and what it delivers

LPN is a book / school-supply distributor running an Oracle/Compiere ERP. Getting business answers out of it today means manual reports. This project replaces that with a local, self-hosted analytics platform that does three things over the same sales data:

💬

Ask in plain language

French/English question → a local LLM writes SQL → it's validated & safely executed → you get a chart + a written narration. No data leaves the building (Ollama runs locally).

📊

Governed BI dashboards

Six pre-built, sub-second dashboard pages (Overview, Revenue/CA, Orders, Articles, Clients, Commercial) served from a curated data mart.

📈

Predictive analytics

A Prophet-based model forecasts monthly chiffre d'affaires (CA) 1–12 months ahead, at company / salesperson / category / theme grain.

Core value: one workflow turns raw ERP exports into (a) ad-hoc Q&A, (b) polished reporting, and (c) forward-looking revenue forecasts — locally, privately, and reproducibly.

How they communicate

All services share a Docker network and talk over HTTP/REST. Frontend → llm-orchestrator (via Vite proxy). The orchestrator fans out to the other services:

Frontend→ llm-orchestrator→ schema-retrieval→ Ollama (SQL)→ sql-validator→ sql-executor→ Postgres

BI dashboard pages skip the LLM entirely and read the pre-built mart views directly.

🔐 Two database roles

lpn_app_admin — read-write, for auth / chat / telemetry in the app schema. lpn_ai_readonly — SELECT-only on business, used by every analytical path (QA, dashboards, forecasting).

AI & Data Pipeline Breakdown

Three pipelines: Text-to-SQL, deterministic BI, and forecasting

3a · Text-to-SQL (the QA pipeline)

Entry point: QaController / QaService in the orchestrator.

  1. Question in — natural language, French or English.
  2. Schema retrieval — SchemaRetrievalClient → embedding search in Qdrant returns only the relevant subset of tables/columns. This is the scaling trick: the LLM never sees the whole catalog, just the handful of tables a question needs.
  3. SQL generation — prompt (sql-generation.en.txt) + retrieved schema → local Ollama (qwen2.5-coder:7b, with a 14b reasoning tier).
  4. Validation — sql-validator (Python/sqlglot) + SemanticSqlValidator in Java. Anything non-SELECT / unsafe is rejected.
  5. Execution — sql-executor runs it as lpn_ai_readonly, search_path=business, with 30s / 10k-row guards.
  6. Narration — AnswerNarrationService sends results back to Ollama (llama3.1) for a human-readable answer.

Every step is timed into app.ai_request_performance_trace; chat history persists per user.

3b · BI dashboards (deterministic — no LLM)

The bi/ package (7 controllers: Overview, Revenue, Orders, Articles, Clients, Commercial + Export) reads pre-materialized mart serving views through dedicated *MartRepository classes → sub-second responses. This is fed by the data-warehouse pipeline:

ERP flat-file exports→ staging→ warehouse (dims + facts)→ mart (serving views)→ BI pages

3c · Predictive / CA forecasting

Service: services-python/predictive. Deterministic ML — no LLM, no Excel at request time.

  • Data flow: reads business.fact_sales_monthly* tables (company / commercial / category / theme grain) as lpn_ai_readonly. Partial months (is_partial=TRUE) are excluded before fitting.
  • Model: Prophet (yearly_fourier_order=5, cps=0.05, multiplicative seasonality) blended 50/50 with a naive lag-12 baseline — the blend beat naive on WAPE (0.222 vs 0.238). Models are cached in-memory per grain/key.
  • Guardrails: requires ≥12 complete months or returns insufficient_history; CA is clamped ≥ 0.
  • Endpoints: /v1/forecast/ca, /v1/forecast/options, /v1/forecast/backtest (hold-out WAPE/MAE/RMSE), /v1/forecast/bakeoff (compares 5 models: seasonal-naive, ETS, SARIMA, tuned Prophet, LightGBM).

📍 Where recent commits landed

🚀 Ripe for a new developer

  • The .NET 9 gateway & reporting services — greenfield placeholders. A natural intern project: build the API gateway and/or a proper reporting service (today's export is frontend-driven).
  • Forecasting UI — wire ForecastsPage fully to the now-live /v1/forecast/* endpoints (confirm it's no longer a mock).
  • Finish the DWH roadmap — resolve the flagged KNOWN GAP (C_TAX / AD_ORG / M_LOCATOR / CUSTOMER_PORTFOLIO have no staging table) and per-file CSV delimiter handling.
  • Schema-retrieval quality — currently a hash embedding backend; swapping in the real multilingual model would improve Text-to-SQL table selection.
  • Data depth — only ~24 months of history limits forecast horizon/confidence; more history (or finer grains) is the main accuracy lever.
